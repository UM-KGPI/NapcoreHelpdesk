Abstract
The deliverable describes the crucial parts of the final version 2 of the Reference Architecture of National Access Points (NAP). The developed NAP Reference Architecture (NRA), including full descriptions and a model available via NAPCORE website, serves as a technical, organizational, and functional
blueprint for creating and harmonizing NAP activities.
This milestone extends the milestone M2.9 “Harmonisation of EU NAP architectures and first layout of
potential NAP federation" where the underlying processes, work steps and status of the NRA were
described. Therefore, the main purpose of this deliverable is to provide a thorough description of the
NRA version 2.0 developed by NAPCORE. It offers an updated and summarized description of the reference architecture creation process and identifies FRAME and its tools as the main methodology. The
document outlines the NAPCORE approach and describes specific guidelines created by NAPCORE for
the development and maintenance of the NRA. It thoroughly depicts the FRAME methodology for creating reference architecture, with detailed descriptions of individual architectural views and the contained object types, tools, and principles utilized in the creation of the NAP Reference Architecture.
Specifically, it provides a general and technical description of the key features of the developed NRA
with quantifications, summary descriptions, and example objects of each developed view, where necessary for in the M2.9 defined NAP types, Metadata directory and Data platform. The Metadata directory contains only information about externally hosted data and services, while the data platform can
also host data and provide access. It also discusses the usability of the NRA through one practical use
case.

1. Introduction
The National Access Point Coordination Organization for Europe (NAPCORE) project aims to enhance
the interoperability of National Access Points (NAPs), which serve as the backbone for European mobility data exchange. NAPs focus on the exchange of static and real-time traffic and travel data, as
mandated by the ITS Directive [23] and its supplementary Delegated Regulations (DRs), to benefit pan-
European drivers and travellers.
Each Member State (MS) is required to establish at least one NAP 1 to ensure the accessibility, exchange, re-use, and updating of data necessary for providing high-quality, continuous travel and traffic
information services across the EU. However, the implementation, functionalities, and organization of
these NAPs were left to the discretion of the Member States, resulting in a diverse landscape of NAPs.
To harmonize technical systems, a unified system architecture and a description of functionalities and
interfaces are essential. Such an architecture defines how systems should interact, ensuring that third
parties do not need to implement different interfaces to interact with these systems. Achieving NAP
interoperability depends on defining a reference architecture.
A system architecture is a conceptual model that defines the structure, behaviour, and more views
of a system. An architecture description is a formal description and representation of a system, organized in a way that supports reasoning about the structures and behaviours of the system.
The architecture could be defined as “ a set of objects and the rules to combine them to make
systems” where these objects could be described on various levels of detail forming a definitive and
consistent framework to guide proposal, development, implementation, and maintenance of ITS.
[17]
An architecture can be described at various levels, including a framework architecture, a reference
architecture, and a specific architecture. The reference architecture consists of:
 Motivational layer: This answers the question of WHY and sets up the system.
 Functional view: This describes the bounded functionalities of the system, with information
exchange (among functionalities, and with other systems). It also describes processes realized
by the functionalities.
 Physical view: This describes how the functionality could be implemented in separate subsystems and identifies the critical interfaces that need to be harmonized.
 Communications view: This describes the interaction and data exchange between the different components of the system.
 Organizational (enterprise) view: This describes the relationships between actors in the system.
 Security view: This provides a high-level overview of the system security.
Depending on the level of detail in the views, the architecture could be further enriched by outputs
such as:
 Common/communication requirements
 Component/interface specification
 Cost-benefit study
 Best practice implementation and guidance material

The NAPCORE task T2.3 aims to develop the NAP Reference Architecture (NAP reference architecture)
considering all existing NAP practices and new requirements emerging from the NAPCORE project using FRAME2 methodology [19]. The task T2.3 has several missions, which aim to result in:
 A shared understanding of general NAP-related terms among the Member States
 Technical guidance on achieving functionalities
 Enhanced comparability of identical features across different NAPs
 Interfaces for international metadata, data, and service exchange
These four pillars form the foundation for any exchange or harmonization activities and shape the
vision of the NAP reference architecture.
The NAP reference architecture describes the minimum required functionalities, processes, and interfaces to enable a harmonized exchange of information (metadata and data) for an EU-wide reuse
of data to create the basis for an EU-wide mobility data space.
The content of the NAP reference architecture should be designed in such a way that each NAP within
Europe can identify the functionalities and artefacts necessary to enable the seamless data exchange.
This consolidates all NAPCORE National Access Point harmonization activities. While this document
does not describe the final architecture due to ongoing developments in NAP harmonization, it does
include and represent all achievements and results currently available within NAPCORE. Future results
and further harmonizations from ongoing NAPCORE developments will be continuously integrated into
the architecture, as outlined in the maintenance procedure.
By utilizing the well-known software, Enterprise Architect, and the most suitable toolkit, FRAME, we
ensure that the architecture is both understandable and future-proof.
The NAP reference architecture can be applied in three different scenarios:
1. To create a harmonized NAP from scratch by implementing the necessary functional and organizational elements using the architecture.
2. To harmonize existing NAPs by updating already existing NAP functionalities and processes in
line with the developed NAP reference architecture.
3. To establish a basis for comparing NAPs by breaking down complex functionalities and processes. Comparisons can also be conducted using the NLKF tool.

4. NAPCORE approach to develop the NAP reference architecture
To achieve the in the Scope and Outline mentioned objectives, task T2.3 aims to define the requirements for the NAP architecture from existing NAPs, data sharing communities and determine how
harmonization shall be approached for the benefit of operators and users. This involves identifying
common NAP elements by comparing different approaches across several NAPs, and identifying minimum required functionalities, processes, and interfaces to enable a harmonized exchange of information.
In Milestone 2.9 [16] the approach definition, exact methodology, used tools to transfer findings and
other procedures were described in detail. This chapter is based on M2.9 but adds new methodologies
like guided documents and enhanced maintenance processes.
This NAP reference architecture consolidates all NAPCORE National Access Point harmonization activities and serves as a technical, organizational, and functional blueprint for creating and harmonizing
existing National Access Points (NAP). This is in accordance with the Delegated Regulations, stakeholder implementations, and best practices, as evaluated through several reviews by various NAPCORE
working groups.
This chapter details our approach to develop the NAP reference architecture, which is a complex system. As mentioned in the NAPCORE Grant Agreement, this work extends the basic FRAME NAP reference architecture based on the requirements gathered as part of T2.1 and gap analysis during workshops, meetings and alignments.
The work started by collecting and selecting the relevant supporting documents for the further development of the NAP reference architecture. Much of this work had already been performed by NAP-
CORE T2.1 which provided descriptions of the main processes of a NAP and in the past under the
FRAME-NEXT project which proposed a first version of the NAP reference architecture.
The feedback was transformed into suggested changes in the organizational, functional, and physical
views of the NAP reference architecture in a series of work meetings.
In addition to the work on architectural views, this task focuses on alignment with other tasks. This is
achieved during regular or ad-hoc joint meetings covering discussion on interoperability, terminology,
and other important harmonization aspects that could be referenced from NAP reference architecture,
such as the interoperability documents.

4.1 Work environment – the FRAME
FRAME, an acronym for the FRamework Architecture Made for Europe, is a minimum stable framework necessary for the deployment of integrated and interoperable ITS and includes a reference architecture for NAPs, which serves as a starting point for this task. FRAME utilizes a highly flexible visual
modelling and design tool Enterprise Architect by SparxSystems, to encompass all necessary functionalities.
The FRAME is a collection of the ready-made framework architecture, methodology and a tool used to
develop reference and specific architectures. The FRAME provides a systematic basis for planning ITS
implementations in Europe, facilitates their integration when deploying multiple systems and helps
ensure interoperability, across European countries.
In the project FRAME NEXT (2017-2021) a NAP Reference Architecture v1.0 [22] based on legal obligations and extrapolated functionalities from the Delegated Regulations was created. To reuse and extend the work done previously, the FRAME architecture methodology was selected for further development of the NAP reference architecture.
NAP reference architecture (NAP reference architecture) is not created from a scratch, it is based
on already created NAP reference architecture within the FRAME-NEXT project. This offers the advantage of a head-start and reuse of previous efforts but also has the potential challenges associated
with legacy issues (disadvantage).
This created a good basis for the harmonisation activities within NAPCORE and to create a common
understanding of NAPs.

4.3.2 Guide to use of Interfaces in Reference Architectures
Interfaces as described a “point of interaction between two systems, entities, or components, facilitating communication and functionality” are a key element for interoperability and basis for crucial
implementation on NAPs.
In different contexts, the term can have specific meanings:
 User Interface (UI): The space where interactions between humans and machines occur. This
includes graphical elements like buttons, icons, and menus in software applications.
 Programming Interface: In software development, an interface defines a set of methods or
functions that a class or system must implement, enabling different software components to
interact.
 Hardware Interface: The physical and logical connections between different hardware components, such as USB ports or network interfaces.
In FRAME, the interface is specified by the analysis of communications requirements of the physical
data flow and identification of related standards and the way the interface is intended to be used.
Therefore, a unified guideline how an interface is described and what is needed to be specified for an
implementation was created. An interface needs to contain following information:
 Type: User Interface, Programming Interface, Hardware Interface
 Short description: usually a sentence mentioning the parts connected via the interface
 Contextual Use: how is the interface intended to be used
 Related documents: any relevant materials + links
 Communication requirements (analysed per functional data flow)
o Data type: raw: static / dynamic / metadata + comment
o max bytes per message: estimation for the largest data we will be transferring
o maximum delay [s]: the tolerance of the receiver to wait for data to be transferred
o message interval: how often are data generated (an approximation needed)
o security level: how sensitive and critical the information is, necessitating high/moderate
or low level of security.
A combination of the information above led to the estimation of needed line capacity.

5.1 The FRAME
The FRAME is a framework that provides a systematic basis for planning ITS implementations in Europe. The FRAME consists of three pillars: architecture, methodology and tools.

ITS service architectures.

FRAME Architecture to implement one or more ITS services.

5.3 FRAME Views and their role in creation of reference architecture
In this chapter the purpose and methodology of different parts of the FRAME process for the creation
of the reference architecture is described. It begins with the Motivational Layer, which defines the
goals, stakeholders, and scope of the service. The User Needs and Requirements View translates these
motivations into specific, testable requirements. The Functional View details the system's functional
structure using hierarchical Data Flow Diagrams. The Physical View describes the deployment of software and hardware components. The Organizational View explains the roles, responsibilities, and relationships of the actors involved. The Communications View focuses on data exchange and interaction between system components. Finally, the Safety and Security View addresses potential hazards
and threats.
5.3.1 Motivational Layer
The Motivation layer documents the reasons for the current effort to create the service as well as the
goals, relevant stakeholders and the scope of the service. The intention of this section is to formulate
an idea of the service, to get an impression of the intended result of its use and to identify the conditions under which it will be used. Naturally, each stakeholder has some aspirations regarding participation in the value creation.
The Motivational Layer outlines the initial position of system development, the stakeholders involved,
and the expected added values and business goals. It includes key elements such as the ITS Vision and
the ITS Service description. This layer models the motivations, reasons for the creation of the ITS Service, and the expectations of its successful implementation. The layer includes stakeholders, represented by actors, who have a vision realized through a mission. This mission, along with their expectations, defines the ITS Service, which in turn provides added value. The ITS Service operates within a
domain and satisfies user needs and requirements.
Once the results of the Motivation analysis are known, those that relate to the desired ITS service can
be developed further. This is done with the assistance of the User Needs.
5.3.2 User Needs and Requirements View
The results of the Motivation analysis are likely to contain a number of ideas, written in a variety of
styles, and which may be open to interpretation. It is therefore necessary to re-write them in a consistent manner, and the User Needs provide a way of expressing these ideas in a way that is Unambiguous, Testable (with objective tests), Traceable (with unique reference numbers) and Singular (with
only one idea at a time). They are therefore written in a standard manner – see below.
The User Needs are split into 10 main groups, which are themselves split further into further subgroups. All the User Needs begin with the words “The system shall …”; this is to ensure that it is clear
what the system should provide and can later be tested to confirm it does.

5.3.3 Functional View
The Functional View focuses on the functional aspects of a system, defining the architectural elements
that deliver its functionality. It documents the system’s functional structure, including key elements,
their responsibilities, and interactions. This view is often the cornerstone of architecture descriptions
and is usually the first part stakeholders read.
The FRAME Architecture uses the Function-Oriented design technique of hierarchical Data Flow Diagrams. The highest level is the Context Diagram, showing the relationship between a system and its
environment (Terminators). The System Boundary separates the ITS under consideration from external
entities like people, organizations, and equipment that interact with it. Terminators can be a person,
organization, or another system (e.g., vehicle).
Figure 7 Context diagram [FRAME, 2015]
At lower hierarchy levels, functionality is described as a chain of functions connected via functional
data flows, with terminators at both ends. This chain represents a data processing sequence in the
designed system. Datastores model real databases by representing the ability of a function to store
and retrieve data.
Functions are structured hierarchically, with rarely more than 10 functions in a single diagram. Higherlevel functions provide a mechanism to manage the large number of low-level functions in the entire
FRAME Architecture.

5.3.5 Organizational View
The Organizational View provides information about actors, their roles and responsibilities, and the
relationships between these roles, whether lawful or contractual. Additionally, it depicts desired business results and processes for ITS deployment, such as ownership, planning, maintenance, deployment, implementation, and tendering. The Organizational View consists of ITS actors performing one
or more roles, agreements between these roles, and their relationships to components (sub-systems)
and modules.
Actors, their roles, the agreements between roles, and the relationship of the roles to the system
(physical view) at different stages of its lifecycle are created by FRAME Architecture End Users using
the FRAME tool as part of the FRAME Methodology. The FRAME methodology provides a guidance of
how roles, including responsibilities, tasks, and capabilities that are typical and necessary for the value
creation of ITS services shall be described. Roles are a significant component of ITS value-added chains,
taken by ITS actors and stakeholders depending on the requirements of the ITS service. A single ITS
actor or stakeholder can occupy one or more ITS roles and vice versa.
In NAPCORE, a detailed definition of the distribution between actor and role has been created, along
with a detailed structure of an agreement object specifying the involved parties, the nature of the
agreement, and the obligations nested in the agreement.
5.3.6 Communications View
The Communications View focuses on the interaction and data exchange between system components (subsystems and modules). It outlines communication protocols, data formats, and interfaces
used for data transmission. This view is crucial for understanding information flow, component interaction, and external system interfaces. It aids in designing efficient communication strategies, ensuring seamless data exchange, and improving overall system performance and reliability.
It extends the Physical View by adding interface definitions to each identified physical data flow, specifying protocols, data models, standards, recommendations, or best practices. Interfaces and specifications are created by FRAME Architecture End Users using the FRAME tool as part of the FRAME
Methodology. This methodology provides guidelines for analysing basic communication requirements, such as data type, message size, delay, frequency, and security, enabling proper interface design.
In NAPCORE, the Interface Specification artefacts were significantly modified along with the way they
are used in the architecture. To support harmonized description, detailed guidelines for interfaces
and specifications were created.
Interface description was adapted to include the purpose, type of interface, and direct links to related
documents describing the interface as a whole. The communications requirements that serve as basis
to identify what type of capacity is needed, were modernized, see chapter 4.3.2 Guide to use of Interfaces in Reference Architectures.
The specifications were adapted in a similar way, allowing to identify specification, provide a brief
description along with its intended use in the ITS system. The specifications were classified into the
following categories: legal document, standard, profile, recommendation and guideline. The specification can be linked to any object in the architecture signifying the origin of the artefacts content and
obligations (mainly for organizational objects) or implying the use of a standards.

5.3.7 Safety and Security View
This View addresses two key aspects: safety and security. Safety refers to freedom from hazards that
can cause physical harm, while security pertains to protection from threats and abuse, including unauthorized disclosure (loss of confidentiality), unauthorized modification (loss of integrity), and unauthorized deprivation of access (loss of availability).
The FRAME methodology assesses safety issues in ITS deployments by creating a "PASSPORT Diagram"
and conducting a “What if?” analysis to identify potential problems. The analysis results in high-level
safety requirements for each subsystem/module, categorized into:
 System safety – due to incorrect system functioning.
 HMI Safety – due to distractions for road users.
 Traffic Safety – due to incorrect vehicle management/behaviour.
Security issues can be complex, covering various types of attacks, from data access to system control.
These attacks can result in denial of service or modification of the service, potentially causing safety
issues. The analysis produces security requirements for each subsystem/module, sorted into problemmitigation pairs.

shared by all ITS Stakeholders. It is a source of inspiration for the ITS Services and provides a clear goal
to be adhered to by the ITS Services.
The ITS Mission is a short statement that highlights what is needed to be done by the ITS Stakeholders
in the present to achieve the ITS Vision. It summarizes the purpose of the existence of the ITS Services
and guides their use by the ITS Actors and/or the end users. It formulates a clearly structured, overarching policy objective of the defined ITS service deployment, considering the interests of stakeholders and end-users.
The ITS Service describes a value-added service provided by ITS actors in the field of transport, traffic,
and mobility for end-users. The added value is created by combining technologies, organizations, processes, and people. The service can be delivered by a single actor or in cooperation with others, and it
creates added value that may consist of individual benefits for mobile travellers, collective benefits for
end-user groups or society, or a mixture of both. It describes the idea and functional elements of the
ITS service as well as framework conditions.
The ITS Domain is a concept that categorizes the diverse applications of ITS into specific fields of application. It applies sector-specific knowledge and additional architectural knowledge to ITS. The domain also defines the boundaries of the ITS system or service at the start of an ITS architecture project,
distinguishing it from similar or adjacent systems or services.

5.4.2 Functional view artefacts
A Function, also known as a “process”, is an action that involves receiving or processing input data.
This data is then either passed on to another function or sent out as information or control instructions
to an external entity. Functions are categorized into various levels: High-Level Functions (HLF) and Low-
Level Functions (LLF). HLFs contain a group of functions concerned with a specific part of data processing and always have component LLFs. LLFs, on the other hand, perform a specific part of the data
input, process, or information output process and have no component functions. User needs are allocated to LLFs, which are the only functions used in the FRAME Methodology.
Data Stores are repositories of data. Many of them are managed by their own dedicated Low-Level
Functions. They store data from, and provide data to, (usually) more than one other Low-Level Function. Thus, Data Stores will always be part of Functional Areas or High-Level Functions.
Data Flows are the movements of data between different components of the system. There are three
types of data flows. The first type is data flows between Low-Level Functions. The second type is data
flows between Low-Level Functions and Data Stores. The third type is data flows between Low-Level
Functions and Terminators/Actors.
Terminators/Actors define the world outside the FRAME Architecture, i.e. artefacts that are not modelled within it. Actors are used to identify variants of a Terminator, e.g. several types of vehicles and
drivers, or the separate roles that a traveller may take during a trip.
5.4.1 Physical view artefacts
Sub-systems are at the highest level and may consist of one or more Modules. The number of Modules
in a Sub-system is optional, and a Sub-system does not need to have any Modules if it lacks complexity.
Sub-systems only exist in one geographic location, meaning that if the ITS deployment is being made
across several locations, each location will have its own Sub-system. Sub-systems and Modules may be
duplicated in total, or in part, in several locations.
Module consists of a computer program or system of computer programs that automate or implement
useful functions. It uses ITS interfaces for communication with other ITS applications and realizes technical activities in an ITS business process. These are parts of Sub-systems in the Physical View of ITS.
They contribute to the functionality of the Sub-systems and can be duplicated in total or partially across
several locations. Modules communicate with each other and with Terminators/Actors through Physical Data Flows.
Physical Data Flows are the means of communication between Sub-systems, Modules, and Terminators/Actors in the Physical View of ITS. There are two types of Physical Data Flows: Internal, which links

5.4.1 Organizational view artefacts
The ITS Actor is part of an ITS value-added chain/network and is directly involved in value creation. It
contributes to the added value of ITS benefits by using its ITS capabilities as part of its activities. It
usually also represents the interests of ITS stakeholders who are not directly involved in the ITS value
chain but have strong associated interests. The ITS end-user is also considered a special ITS actor.
The ITS Role defines and describes responsibilities, tasks, and capabilities that are typical and necessary for the value creation of ITS services. Is taken by ITS actors and stakeholders depending on the
requirements of the ITS service to be implemented. A single ITS actor or stakeholder can occupy one
or more ITS roles.
The ITS Agreement, Agreement is contractual or lawful relationship between two roles, that defines
obligations/responsibilities of the roles to each other and also the obligations/responsibilities of the
roles in this relationship to other roles. The Agreement could take the form of a European or national
legislative document, memorandum of understanding, contract, license, or terms and conditions.

specification consisting of the definition of a protocol and a data model and is used and implemented
by ITS applications.
The Specification is detailed, precise description of the requirements, design, behaviour, or characteristics of a system, component, or process. Specifications are used to ensure that everyone involved in
a project understands what is expected and to provide a basis for verifying that the final product meets

7. Practical use of the NAP reference architecture
7.1 Scope of application and benefits of NAP reference architecture
The NAP reference architecture, based on the European ITS Framework Architecture (FRAME) methodology, outlines all harmonized functionalities and procedures of National Access Points (NAPs) and
their interactions. Its scope of application includes:
 Defining NAP Types and Terms: Establishing specific terms for mutual understanding.
 Harmonized Data Definitions: Displaying harmonized data type definitions from Data Registries (DRs) to aid implementation and set user expectations.
 Dataset Descriptions: Specifying metadata, naming conventions, and use of keywords to enhance user search experience.
 Technical Interfaces: Specifying technical interfaces to facilitate access to data from multiple
NAPs for service providers (NAP content consumers).
 Cost-Benefit Analysis: Conducting cost-benefit analysis to plan the implementation of additional NAP features.
The NAP reference architecture aims to harmonize NAP activities at the European level and increase
their effectiveness. It defines roles, functions, and processes for NAP users, data registration, and
data/metadata retrieval. It also outlines the minimum functionality for the two basic NAP types at the
national level: Metadata Directory and Data Platform.
The design principles of the NAP reference architecture are simplicity, transferability, and understandability. Utilizing the NAP reference architecture should yield benefits such as:
 European Compatibility: Ensuring compatibility at the European level with minimum components and detailed system functionality.
 Gap Identification: Identifying gaps, harmonization needs, and emerging requirements in system specifications.
 Inclusion of New Systems: Facilitating the inclusion of new systems or components through
technical system descriptions.
 Improved Usability: Enhancing usability based on gathered experience and evolving user
needs.
 Enhanced Planning: Improving the planning of implementation phases, goal documentation,
and result comparison.

8. Conclusions
This report outlines the process of creating a harmonized NAP reference architecture (NRA), the
FRAME methodology used for its development, the final product (NRA version 2.0) and provides an
example of usage. The NRA consolidates all NAPCORE National Access Point harmonization activities.
While this document does not detail every part of the NRA, it highlights the key building elements of
different views, how they interact within the NRA and on examples documents the qualitative aspect
of their content with.
8.1 Challenges and lessons learned
Updating the NAP reference architecture within the NAPCORE project presented significant challenges
beyond the actual content of the architecture. One of the initial challenges was aligning terminology
for NAP implementations, specifically the two types: Metadata Directory and Data Platform, many different labels used by NAP operators highlighted the importance of having common terminology.
Having two NAP types created a challenge in addressing their similarities and differences within the
architecture. The decision to model the Data Platform on top of the Metadata Directory simplified the
number of diverse artifacts but caused issues when describing functionalities that crossed type boundaries, adding complexity to the model.
Updating individual views was challenging because the FRAME methodology did not provide detailed
guidance for creating reference architectures. The FRAME metamodel of the Motivation Layer lacked
interactions between expectations and services, services and added values, and stakeholders. The
methodology for the Organizational View did not precisely cover the expected content of actors, roles
and agreements objects. The Physical View required alignment with already published and used terminology. In the Communications View, the interface and specification objects lacked precise explanations. We overcame these challenges by updating and detailing the methodology, adapting the FRAME
model, updating the tool, and providing additional explanations and guidance, such as for the creation
of specifications [6] and interfaces [5].
8.2 Outcomes and results
The NAP Reference architecture was developed for two NAP types, the Metadata Directory and Data
Platform. It consists of these views and supplements:
 Motivational Layer, which defines NAP scope, goals, stakeholders, expectations and benefits.
 User Needs View that translates motivations into specific, testable predefined requirements.
 Functional View that details the NAPs functional structure using Data Flow Diagrams.
 Physical View describing the deployment of software and hardware components of NAP allowing for planned deployment.
 Organizational View explaining the roles, responsibilities, and relationships of the actors involved in NAP ecosystem.
 Communications View focusing on data exchange and interaction between system components by identifying and describing interfaces.
 Safety and Security View that addresses potential hazards and threats.
 KPI Framework supplement that provides a link between NAP LoS KPI framework (NLKF tool)
and the NAP reference architecture.
 Specifications and Requirements supplement providing a pool of identified, legal and technical documents related to the NAP development that could be mapped to the parts of the
NAP architecture

The architecture is a living document, subject to updates based on strategic, political, legal, and technical developments. Future results and further harmonizations from post-project NAPCORE developments will be continuously integrated into the architecture according to the developed maintenance
procedure. By utilizing the well-known software, Enterprise Architect, and the most suitable toolkit,
FRAME, we ensure that the architecture is both understandable and future-proof.
For these future updates, the NAP reference architecture will be available on GitHub under an open
license, and issues raised by maintainers or other parties will be addressed during regular releases.
